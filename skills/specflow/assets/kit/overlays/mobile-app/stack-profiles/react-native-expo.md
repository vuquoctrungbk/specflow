# Stack profile react-native-expo

## 1. Scope

A mobile app written in TypeScript on React Native and Expo SDK 57, with navigation by Expo Router, on-device data in SQLite through `expo-sqlite`, tokens in `expo-secure-store`, display strings through i18next, and API types generated from OpenAPI. The profile matches a project generated by `create-expo-app` 5.0.0 (default template, `src/app/` directory) plus the libraries in §2.

The versions were pinned on 2026-09-22 and tried together on Node.js 24.21.0 with a trial project: type generation, lint, typecheck, component unit tests, integration tests of the sync engine on `node:sqlite` (two conflicting devices, many simultaneous triggers, a lost response followed by a resend, chained changes, an edit made while a change to the same record is being sent, a sync before the retry time, received data that cannot be saved), the JavaScript bundle for iOS and Android, `expo-doctor` and `npm audit` all passed; the setup steps in §6 were rerun on a fresh scaffold. Not tried in the environment where the profile was written: Maestro e2e (needs an emulator or a device), native builds with EAS Build and submission to the stores (need an Expo account and developer accounts), and the query port on `expo-sqlite` running on a real device; this port shares the queueing function with the test adapter (§4.2) so that transaction behavior is the same. The project runs these two parts for the first time on its own CI and records the result in ARCHITECTURE §13 before Gate 2. Raise versions under the Dependency Policy in ARCHITECTURE §2.2.

### 4.2. Local Database and API Client (for ARCHITECTURE §5)

<!-- PROFILE-CONTENT: arch.schema -->
### Stack Local Database & API Client

- All SQLite access goes through the `SqlExecutor` port; the app uses the implementation on `expo-sqlite`, and integration tests use the implementation on Node.js's `node:sqlite` with the same migrations. Both open exactly one connection and wrap it with `serializeConnection`: calls queue up, and a transaction (`BEGIN IMMEDIATE` to `COMMIT`) holds the connection until it ends, so no other statement gets in between. Do not use `withExclusiveTransactionAsync`: it opens a second connection for each transaction, on which foreign keys are off and parallel writes fail with `database is locked`, unlike in the tests.
- `PRAGMA foreign_keys` and `busy_timeout` take effect per connection, so set them right after opening the single connection.
- Migrations are an append-only list of scripts; `PRAGMA user_version` records the number of migrations that have run. The database is opened with `enableChangeListener: true` so that hooks query again when a related table changes.
- The shared client is created with `openapi-fetch` and receives `fetch` as a parameter, so that integration tests can replace it with a mock API. The authentication header is attached by the `client.use(...)` middleware following the session mechanism in ARCHITECTURE §6.1.

```typescript
export type SqlValue = string | number | null;

// Port over the on-device database: expo-sqlite in the app, node:sqlite in integration tests.
export interface SqlExecutor {
  exec(script: string): Promise<void>;
  run(sql: string, params?: readonly SqlValue[]): Promise<void>;
  all<T>(sql: string, params?: readonly SqlValue[]): Promise<T[]>;
  transaction(task: (tx: SqlExecutor) => Promise<void>): Promise<void>;
}
```

```typescript
import type { SqlExecutor, SqlValue } from "./sql-executor";

export type SqlConnection = Pick<SqlExecutor, "exec" | "run" | "all">;

// The app opens one connection. Calls queue behind each other and a transaction owns the connection until it ends,
// so no statement from elsewhere runs inside it. The app adapter and the test adapter share this code.
export function serializeConnection(connection: SqlConnection): SqlExecutor {
  let tail: Promise<unknown> = Promise.resolve();
  const exclusive = <T>(task: () => Promise<T>): Promise<T> => {
    const result = tail.then(task, task);
    tail = result.catch(() => undefined);
    return result;
  };
  const insideTransaction: SqlExecutor = {
    exec: (script) => connection.exec(script),
    run: (sql, params) => connection.run(sql, params),
    all: <T>(sql: string, params?: readonly SqlValue[]) => connection.all<T>(sql, params),
    transaction: () => Promise.reject(new Error("nested transactions are not supported")),
  };
  return {
    exec: (script) => exclusive(() => connection.exec(script)),
    run: (sql, params) => exclusive(() => connection.run(sql, params)),
    all: <T>(sql: string, params?: readonly SqlValue[]) => exclusive(() => connection.all<T>(sql, params)),
    transaction: (task) =>
      exclusive(async () => {
        await connection.exec("BEGIN IMMEDIATE");
        try {
          await task(insideTransaction);
          await connection.exec("COMMIT");
        } catch (error) {
          // SQLite may already have rolled back on its own; the original error is the one that matters.
          await connection.exec("ROLLBACK").catch(() => undefined);
          throw error;
        }
      }),
  };
}
```

```typescript
import { openDatabaseAsync } from "expo-sqlite";
import { migrate } from "./migrations";
import { serializeConnection } from "./serialize-connection";
import type { SqlExecutor, SqlValue } from "./sql-executor";

// One connection for the whole app. withExclusiveTransactionAsync is not used: it opens a second connection,
// on which foreign keys are off and concurrent writes fail with "database is locked".
export async function openAppDatabase(name: string): Promise<SqlExecutor> {
  const db = await openDatabaseAsync(name, { enableChangeListener: true });
  await db.execAsync("PRAGMA journal_mode = WAL; PRAGMA foreign_keys = ON; PRAGMA busy_timeout = 5000;");
  const executor = serializeConnection({
    exec: (script) => db.execAsync(script),
    async run(sql, params = []) {
      await db.runAsync(sql, [...params]);
    },
    all: <T>(sql: string, params: readonly SqlValue[] = []) => db.getAllAsync<T>(sql, [...params]),
  });
  await migrate(executor);
  return executor;
}
```

```typescript
import type { SqlExecutor } from "./sql-executor";

// Append-only: a released migration is never edited; PRAGMA user_version records how many ran.
export const MIGRATIONS: readonly string[] = [
  `CREATE TABLE sync_state (id INTEGER PRIMARY KEY CHECK (id = 1), cursor TEXT, last_synced_at TEXT);
   INSERT INTO sync_state (id) VALUES (1);`,
];

export async function migrate(db: SqlExecutor): Promise<void> {
  const [row] = await db.all<{ user_version: number }>("PRAGMA user_version");
  for (let version = row?.user_version ?? 0; version < MIGRATIONS.length; version++) {
    const script = MIGRATIONS[version];
    if (script === undefined) break;
    await db.transaction(async (tx) => {
      await tx.exec(script);
      await tx.exec(`PRAGMA user_version = ${version + 1}`);
    });
  }
}
```

### 4.3. Stack Conventions (for ARCHITECTURE §7)

<!-- PROFILE-CONTENT: arch.conventions -->
### Stack Implementation Notes

- A screen is a file in `src/app/`; the root `_layout.tsx` keeps the splash screen (`expo-splash-screen`) until the database is open and migrations have run, then provides `SqlExecutor`, the API client and the sync engine through React context. Navigation parameters are read with `useLocalSearchParams` and validated with Zod before use.
- Hooks that read data use `useLocalQuery`: it queries locally, then queries again when `addDatabaseChangeListener` reports a change in a related table; SQLite reports every changed row, so reports within one frame are merged into one query. The list of tables passed in is a constant or is memoized.

  ```typescript
  import { addDatabaseChangeListener } from "expo-sqlite";
  import { useCallback, useEffect, useState } from "react";
  import type { SqlExecutor, SqlValue } from "./sql-executor";

  // Re-runs a local query when one of the given tables changes (the database is opened with enableChangeListener).
  // SQLite reports every changed row, so the reloads of one burst of changes are merged into one.
  export function useLocalQuery<T>(db: SqlExecutor, sql: string, params: readonly SqlValue[], tables: readonly string[]) {
    const [rows, setRows] = useState<T[] | undefined>(undefined);
    const [error, setError] = useState<unknown>(undefined);
    const key = JSON.stringify(params);
    const load = useCallback(() => {
      db.all<T>(sql, JSON.parse(key) as SqlValue[]).then((next) => {
        setRows(next);
        setError(undefined);
      }, setError);
    }, [db, sql, key]);
    useEffect(() => {
      load();
      let pending: ReturnType<typeof setTimeout> | undefined;
      const subscription = addDatabaseChangeListener((event) => {
        if (!tables.includes(event.tableName) || pending !== undefined) return;
        pending = setTimeout(() => {
          pending = undefined;
          load();
        }, 16);
      });
      return () => {
        clearTimeout(pending);
        subscription.remove();
      };
    }, [load, tables]);
    return { rows, error };
  }
  ```
- The sync engine wraps a sync run with `createSingleFlight` and runs exactly one more run for a trigger that arrives midway when the run ends with `done` or `offline`; the triggers are: once when the database finishes opening, `addNetworkStateListener` of `expo-network` (when `isInternetReachable` is `true`), `AppState` (when the app returns to `active`), pull to refresh (`RefreshControl`), and a timer while the app is open.
  - The first four triggers drop the backoff's retry time before syncing (only the device's `429` wait is kept); when a run ends, the timer is set to the end of the `429` wait when no run has started after it, otherwise to the nearest retry time still pending, including a retry time that passed while that run was running (a one-second delay is used then instead of skipping it), unless the run ended with `auth-required` or `failed`; the first run that starts after the `429` wait ends clears it, so that wait sets no further timer; the timer is cancelled when the app goes to the background or when the registration is removed.
  - Refreshing the session on a `401` uses `createSingleFlight(refresh, () => false)` so that a burst of `401` responses refreshes only once.

  ```typescript
  // Runs one task at a time; calls that arrive during a run share it and schedule exactly one more run.
  export function createSingleFlight<T>(task: () => Promise<T>, runAgain: (result: T) => boolean = () => true): () => Promise<T> {
    let running: Promise<T> | null = null;
    let again = false;
    return () => {
      if (running) {
        again = true;
        return running;
      }
      running = (async () => {
        let result: T;
        do {
          again = false;
          result = await task();
        } while (again && runAgain(result));
        return result;
      })().finally(() => {
        running = null;
      });
      return running;
    };
  }
  ```
- Change IDs and idempotency keys are generated with `randomUUID()` of `expo-crypto` and stored with the change in the queue before sending.
- The refresh token is stored with `SecureStore.setItemAsync` and `keychainAccessible: SecureStore.AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` (readable when a sync runs after the device has been unlocked once, and it does not travel with a backup to another device); the access token is kept in memory only.
- Backup: `app.json` sets `android.allowBackup` to `false`. On iOS, `expo-sqlite` places the database in the app's `Documents/SQLite` directory, which belongs to the iCloud and computer backups; ARCHITECTURE §9 records this risk or a dedicated measure.
- Display strings: one i18next instance created with `createInstance()` and `initReactI18next`, the locale taken from `getLocales()` of `expo-localization`, one JSON file per locale in `src/i18n/`; plurals use the suffixes `_one` and `_other`. Components use `useTranslation`.
- Theme: `src/theme/tokens.ts` maps from the `semantic` tokens of `docs/design-system/tokens.json` (one set of values per mode) and is the only place that holds raw color, spacing, radius and font size values; `use-theme.ts` picks the set by `useColorScheme` of `react-native`. Component styles read values only from this hook. Style Dictionary is an option for generating the file and is not installed by default; while it is not used, write `tokens.ts` by hand from the tokens and keep it in step with `tokens.json`.
- Accessibility: an interactive element has `accessibilityRole` and `accessibilityLabel`; enumerated values (results, statuses) are read by the label in the string file, not by the raw code; sync status announcements use `accessibilityLiveRegion="polite"` on Android and `AccessibilityInfo.announceForAccessibility` on iOS; tests query with `getByRole` and `getByLabelText`. An element that a Maestro flow touches has a `testID`.
- Environment variables: only variables with the `EXPO_PUBLIC_` prefix are embedded in the build, and only when the code reads them in the form `process.env.EXPO_PUBLIC_API_BASE_URL`, not by a string index. `src/config/env.ts` is the only place that reads variables:

  ```typescript

  ```

The `node:sqlite` adapter for integration tests (`test/support/node-sqlite-executor.ts`) uses the same `serializeConnection` as the app, so transactions in tests and on the device behave the same way:

```typescript
import { DatabaseSync } from "node:sqlite";
import { migrate } from "@/db/migrations";
import { serializeConnection } from "@/db/serialize-connection";
import type { SqlExecutor, SqlValue } from "@/db/sql-executor";

// Same port and the same serialization as the app, backed by node:sqlite in memory.
export async function openTestDatabase(): Promise<SqlExecutor> {
  const db = new DatabaseSync(":memory:");
  db.exec("PRAGMA foreign_keys = ON");
  const executor = serializeConnection({
    async exec(script) {
      db.exec(script);
    },
    async run(sql, params = []) {
      db.prepare(sql).run(...params);
    },
    async all<T>(sql: string, params: readonly SqlValue[] = []) {
      return db.prepare(sql).all(...params) as T[];
    },
  });
  await migrate(executor);
  return executor;
}
```

The mock API of the `CONC` test is a class with a `fetch` method that takes a `Request`, keeps record versions, stores responses by the `Idempotency-Key` header, records the key and body of every request, has a flag that loses the next response after it has been applied, a hook that runs a task after the next write is applied and before it replies (to test a local write while a change is being sent), a hook that runs a task before it replies to the next read (to test a trigger that arrives while a read is in flight), a switch that makes one record always return a `5xx` error, and an optional delay; the test creates the client with `createApiClient(baseUrl, api.fetch)`. Tests of local writes do not need the API: `test/support/` has a function that puts sample records into the database as they would be after a sync run. Tests import `describe`, `it` and `expect` from Jest's globals. Test names describe behavior in English, for example `it("keeps both edits when two devices change the same item offline", ...)`; they contain no TC ID.

## 5. Stack Conventions

- Install packages with native code or packages that belong to the SDK with `npx expo install`, then pin them to the exact version with `npm install --save-exact`; install pure JavaScript packages directly with `npm install --save-exact`. `npx expo install` writes the package into dependencies even when `-- --save-dev` is added, so install packages used only for tests and tooling with `npm install --save-dev --save-exact`.
- Do not create or edit the `ios/` and `android/` directories by hand; native configuration lives in `app.json` and config plugins. Adding a library with native code needs a new development build (`npx expo run:ios`, `npx expo run:android` or EAS Build); Expo Go cannot run it.
- `create-expo-app` generates `AGENTS.md` containing Expo's guidance, a one-line `CLAUDE.md` with `@AGENTS.md`, and `.claude/settings.json` that enables the Expo plugin for Claude Code. Keep `AGENTS.md` and `.claude/settings.json` as they are; when the app sits at the repo root, replace the scaffold's `CLAUDE.md` with the file generated from the Agent Context Template, then add at the end a precedence line and the `@AGENTS.md` line so that Claude Code loads Expo's version-specific guidance. `AGENTS.md` recommends `npx expo install --fix`, `eas-cli@latest` and over-the-air updates; these points yield to the versions pinned in ARCHITECTURE §2, the Dependency Policy and the release policy in ARCHITECTURE §8. The precedence line: "When `AGENTS.md` conflicts with this file, `docs/ARCHITECTURE.md` or `.claude/rules/`, those files win."; when the app sits in a subdirectory, keep the scaffold's one-line `CLAUDE.md` in that directory, and the project's Agent Context lives at the repo root. specflow's rules live in `.claude/rules/` next to `.claude/settings.json`.
- A form schema copies the limits from the API's contract and has boundary tests; sharing a schema package with the API needs an ADR.
- Code specific to one platform goes in files with the suffix `.ios.tsx` or `.android.tsx`; `Platform.OS` is used only for small differences within a single line.
